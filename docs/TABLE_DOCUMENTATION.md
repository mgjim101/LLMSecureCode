# Data Cleanup - Table Documentation

This section documents cleanup artifacts in `data_cleanup/` and the scripts that generate equivalent outputs in `outputs/`.

## Scope

- Data cleanup artifacts documented here:
  - `data_cleanup/filter_limesurvey_ids.csv`
  - `data_cleanup/complete_submissions.txt`
  - `data_cleanup/prolific_ids_with_counts.txt`
  - `data_cleanup/prolific_ids_with_counts.csv`
- Main generation code:
  - `data_cleanup/filter_limesurvey.py`
  - `data_cleanup/find_complete_prolific_ids.py`

## Source Tables and Inputs

- `Tool_CSV/results-survey641369.csv`
  - Source for LimeSurvey filtering in `filter_limesurvey.py`.
- `Tool_CSV/participants.csv`
  - Maps `prolific_pid` to `participant_id`.
- `Tool_CSV/code_snapshots.csv`
  - Used to verify participant has code snapshot data.
- `Tool_CSV/tool_usage.csv`
  - Used to verify participant has tool usage data.
- `outputs/complete_submissions.txt` (or fallback `complete_submissions.txt`)
  - Candidate complete Prolific IDs used by `find_complete_prolific_ids.py`.

## Important Derivation Rules

- `filter_limesurvey.py`:
  - Filters `results-survey641369.csv` where
    - `Please paste here the confirmation code generated by the tool. ` equals `761528`.
  - Extracts IDs from `Unnamed: 7`.
  - Writes a single-column CSV named `prolific_id`.
- `find_complete_prolific_ids.py`:
  - Starts from Prolific IDs in `complete_submissions.txt`.
  - Maps each to `participant_id` via `participants.csv`.
  - Keeps IDs whose mapped participant appears in both:
    - `code_snapshots.csv`, and
    - `tool_usage.csv`.
  - Also flags potential duplicate submissions where a `prolific_pid` appears multiple times in `participants.csv`.

## File: `filter_limesurvey_ids.csv`

Filtered Prolific IDs that match the target confirmation code from survey results.

Columns:
- `prolific_id`: Prolific identifier extracted from `Unnamed: 7` in survey CSV.

Primary use:
- Candidate inclusion list based on survey confirmation code.

## File: `complete_submissions.txt`

Plain-text candidate list of complete Prolific submissions used as input by downstream filtering.

Contents:
- Header line (for example `Found N IDs:`).
- One Prolific ID per line.

Primary use:
- Initial pool of IDs before cross-checking study telemetry tables.

## File: `prolific_ids_with_counts.txt`

Human-readable filtered list of Prolific IDs with linked participant and row-count diagnostics.

Contents per matched ID line:
- `prolific_id`
- `participant_id`
- `code_snapshots=<count>`
- `tool_usage=<count>`

Also includes:
- Total matched ID count.
- Duplicate-submission section (`None found.` or duplicate lines).

Primary use:
- Auditable inclusion list used by many downstream analysis scripts.

## File: `prolific_ids_with_counts.csv`

Structured version of the same filtering/diagnostic output.

Columns:
- `section`:
  - `match` for accepted IDs.
  - `duplicate` for potential duplicate survey submissions.
- `prolific_id`: Prolific identifier.
- `participant_id`: mapped internal participant id.
- `code_snapshots`: row count in `Tool_CSV/code_snapshots.csv` (for `match` rows).
- `tool_usage`: row count in `Tool_CSV/tool_usage.csv` (for `match` rows).
- `occurrences`: number of occurrences in `participants.csv` (for `duplicate` rows).

Primary use:
- Machine-readable inclusion diagnostics for reproducible filtering.

## Notes and Caveats

- Script outputs are written to `outputs/`; mirrored copies may appear under `data_cleanup/`.
- `filter_limesurvey.py` depends on exact survey column names (`Unnamed: 7` and the long confirmation-code column label).
- `prolific_ids_with_counts.*` act as foundational inputs for multiple later analyses in this repository.

# Bandit Comparison With Tool - Table Documentation

This section describes the CSV outputs produced by `bandit_comparison_with_tool/bandit_comparison.py`, including how each table is derived and how it relates to source tables in `Tool_CSV/`.

## Scope

- Output tables documented here:
  - `bandit_comparison_with_tool/bandit_comparison_llm_tasks.csv`
  - `bandit_comparison_with_tool/bandit_comparison_participant_submissions.csv`
  - `bandit_comparison_with_tool/bandit_comparison_type_changes.csv`
  - `bandit_comparison_with_tool/bandit_comparison_nudge_counts.csv`
  - `bandit_comparison_with_tool/bandit_comparison_nudge_task_total_diffs.csv`
  - `bandit_comparison_with_tool/bandit_comparison_nudge_total_diffs.csv`
- Main generation code:
  - `bandit_comparison_with_tool/bandit_comparison.py`

## Source Tables and Inputs

- `Tool_CSV/code_snapshots.csv`
  - Used to collect code by `(participant_id, taskid)` for `eventid` 2 and 4.
  - Event meaning reference: `Tool_CSV/event_types.csv`:
    - `2` = `RUN_TOOL`
    - `4` = `SUB_TOOL`
- `Tool_CSV/participants.csv`
  - Used to derive `nudge` group label from `group_id`:
    - `group_id` 1-6 -> nudge `A`
    - `group_id` 7-12 -> nudge `B`
- `outputs/prolific_ids_with_counts.txt`
  - Used as a participant filter (only listed participants are included).
- `LLMCode/task*.json`
  - Baseline LLM task code used for comparison by `task_id`.

## Important Derivation Rules

- A participant-task pair is included only if code changed between:
  - earliest `eventid=2` code, and
  - latest `eventid=4` code.
- Bandit runs on:
  - all LLM baseline tasks, and
  - each changed participant submission (`eventid=4` code).
- Severity diff columns are **submitted minus baseline LLM**.
- `total_diff_issue_count` is recomputed as:
  - `total_diff_high_severity + total_diff_medium_severity + total_diff_low_severity`
  - (not a sum of raw `issue_count`).

## Shared Keys Across Output Tables

- `task_id`: task identifier (`1`, `2`, `3` in current data).
- `participant_id`: participant identifier from source data.
- `nudge`: derived cohort label (`A` or `B`).

## Table: `bandit_comparison_llm_tasks.csv`

One row per LLM baseline task (no participant dimension).

Columns:
- `task_id`: task id from `LLMCode/task*.json`.
- `issue_count`: total Bandit issues in baseline task code.
- `high_severity`: count of HIGH-severity baseline issues.
- `medium_severity`: count of MEDIUM-severity baseline issues.
- `low_severity`: count of LOW-severity baseline issues.

Primary use:
- Baseline security profile per task for downstream comparisons.

## Table: `bandit_comparison_participant_submissions.csv`

One row per changed `(participant_id, task_id)` submission analyzed.

Columns:
- `participant_id`: participant id.
- `nudge`: participant cohort (`A`/`B`) derived from `participants.csv`.
- `task_id`: task id.
- `issue_count`: total Bandit issues in participant submitted code (`eventid=4`).
- `high_severity`: HIGH-severity count in participant submitted code.
- `medium_severity`: MEDIUM-severity count in participant submitted code.
- `low_severity`: LOW-severity count in participant submitted code.
- `severity_diff_high`: submitted HIGH minus LLM baseline HIGH for same `task_id`.
- `severity_diff_medium`: submitted MEDIUM minus LLM baseline MEDIUM for same `task_id`.
- `severity_diff_low`: submitted LOW minus LLM baseline LOW for same `task_id`.

Primary use:
- Participant-level outcome table for modeling or aggregation.

## Table: `bandit_comparison_type_changes.csv`

Long-form issue-type transitions per changed submission.

Columns:
- `participant_id`: participant id.
- `nudge`: participant cohort (`A`/`B`).
- `task_id`: task id.
- `type_id`: Bandit test id (for example `B311`, `B603`).
- `type_name`: Bandit test name (for example `blacklist`).
- `change_kind`:
  - `new`: type appears in submitted code but not baseline.
  - `fixed`: type appears in baseline but not submitted code.
  - `common`: type appears in both baseline and submitted code.

Primary use:
- Analyze which vulnerability families are introduced or fixed.

## Table: `bandit_comparison_nudge_counts.csv`

Aggregated totals by `(nudge, task_id)` based on participant submissions.

Columns:
- `nudge`: `A` or `B`.
- `task_id`: task id.
- `n`: number of changed submissions in the group.
- `total_issue_count`: sum of `issue_count` across group rows.
- `total_high_severity`: sum of `high_severity` across group rows.
- `total_medium_severity`: sum of `medium_severity` across group rows.
- `total_low_severity`: sum of `low_severity` across group rows.

Primary use:
- Cohort/task-level burden of observed vulnerabilities in submitted code.

## Table: `bandit_comparison_nudge_task_total_diffs.csv`

Aggregated baseline-vs-submission severity differences by `(nudge, task_id)`.

Columns:
- `nudge`: `A` or `B`.
- `task_id`: task id.
- `n`: number of changed submissions in the group.
- `total_diff_issue_count`: net severity-based issue difference for group.
- `total_diff_high_severity`: sum of `severity_diff_high`.
- `total_diff_medium_severity`: sum of `severity_diff_medium`.
- `total_diff_low_severity`: sum of `severity_diff_low`.

Interpretation:
- Positive value => more issues in participant code than baseline.
- Negative value => fewer issues than baseline.

## Table: `bandit_comparison_nudge_total_diffs.csv`

Overall diff totals by `nudge` across all tasks.

Columns:
- `nudge`: `A` or `B`.
- `task_groups`: number of `(nudge, task_id)` groups included.
- `n_submissions`: total changed submissions across all tasks.
- `total_diff_issue_count`: net severity-based issue difference across tasks.
- `total_diff_high_severity`: total HIGH diff across tasks.
- `total_diff_medium_severity`: total MEDIUM diff across tasks.
- `total_diff_low_severity`: total LOW diff across tasks.

Primary use:
- High-level cohort comparison of security change direction and magnitude.

## Relationship Diagram (Conceptual)

- `code_snapshots.csv` + participant filter -> changed submissions (`event 2` vs `event 4`) -> Bandit -> participant-level table.
- `participants.csv` -> `nudge` mapping -> enrich participant-level and all downstream aggregates.
- `LLMCode/task*.json` -> Bandit baseline -> per-task baseline table + comparison anchor for all diffs and type changes.

## Notes and Caveats

- Tables include only participants present in `outputs/prolific_ids_with_counts.txt`.
- Tables include only tasks where participant code changed between event 2 and event 4.
- `tool_usage.csv`, `tasks.csv`, and `nudge_descriptions.csv` are not directly read by this script, but provide adjacent experimental context.

# Code Changes With Tool - Table Documentation

This section documents CSV outputs in `code_changes_with_tool/`, produced by comparing participant code snapshots before and after tool usage.

## Scope

- Output tables documented here:
  - `code_changes_with_tool/code_changes_after_tool_tasks.csv`
  - `code_changes_with_tool/code_changes_after_tool_summary.csv`
  - `code_changes_with_tool/code_changes_after_tool_nudge_counts.csv`
- Main generation code:
  - `code_changes_with_tool/code_changes_after_tool.py`

## Source Tables and Inputs

- `Tool_CSV/code_snapshots.csv`
  - Used to collect code by `(participant_id, taskid)` for `eventid` 2 and 4.
  - Event meaning reference: `Tool_CSV/event_types.csv`:
    - `2` = `RUN_TOOL` (start snapshot)
    - `4` = `SUB_TOOL` (end snapshot)
- `Tool_CSV/participants.csv`
  - Used to derive `nudge` group label from `group_id`:
    - `group_id` 1-6 -> nudge `A`
    - `group_id` 7-12 -> nudge `B`
- `outputs/prolific_ids_with_counts.txt`
  - Used as participant filter for analysis scope.

## Important Derivation Rules

- The script keeps:
  - earliest `eventid=2` snapshot per `(participant_id, taskid)`, and
  - latest `eventid=4` snapshot per `(participant_id, taskid)`.
- A task pair is analyzable only when both events exist.
- `changed` is computed by string equality on full code text:
  - `True` if `eventid=2` code differs from `eventid=4` code.
  - `False` otherwise.
- Line-based metrics:
  - `start_lines` and `end_lines` are `len(code.splitlines())`.
  - `line_delta = end_lines - start_lines`.

## Shared Keys Across Output Tables

- `participant_id`: participant identifier.
- `nudge`: derived cohort label (`A` or `B`).
- `taskid` / `task_id`: task identifier (note naming differs across files).

## Table: `code_changes_after_tool_tasks.csv`

Task-level results for each analyzable `(participant_id, taskid)` pair.

Columns:
- `participant_id`: participant id.
- `nudge`: participant cohort (`A`/`B`).
- `taskid`: task id.
- `changed`: boolean indicating whether code changed from event 2 to event 4.
- `start_lines`: line count in start code (`eventid=2`).
- `end_lines`: line count in end code (`eventid=4`).
- `line_delta`: `end_lines - start_lines`.
- `start_timestamp`: timestamp of selected start snapshot.
- `end_timestamp`: timestamp of selected end snapshot.

Primary use:
- Most granular table for auditing participant-level post-tool edits.

## Table: `code_changes_after_tool_summary.csv`

Participant-level aggregation over task pairs in scope.

Columns:
- `participant_id`: participant id.
- `nudge`: participant cohort (`A`/`B`).
- `tasks_analyzed`: number of analyzable task pairs for the participant.
- `changed_task_count`: count of tasks with `changed=True`.
- `unchanged_task_count`: count of tasks with `changed=False`.
- `has_any_change`: boolean flag (`True` if `changed_task_count > 0`).

Primary use:
- Per-participant behavior summaries after tool usage.

## Table: `code_changes_after_tool_nudge_counts.csv`

Aggregated change counts by `(nudge, task_id)`.

Columns:
- `nudge`: `A` or `B`.
- `task_id`: task id.
- `n`: number of participant task pairs in this group.
- `changed_count`: number of pairs with code changes.
- `unchanged_count`: number of pairs without code changes.

Primary use:
- Cohort/task-level comparison of editing frequency after tool use.

## Notes and Caveats

- Only participants listed in `outputs/prolific_ids_with_counts.txt` are considered.
- Participant-task pairs missing either event 2 or event 4 are excluded from CSV outputs.
- Task identifier naming differs by file:
  - `taskid` in `code_changes_after_tool_tasks.csv`
  - `task_id` in `code_changes_after_tool_nudge_counts.csv`

# Tool Usage - Table Documentation

This section documents CSV outputs in `tool_usage/`, generated from tool-decision events for participants in scope.

## Scope

- Output tables documented here:
  - `tool_usage/tool_usage_participant_summary.csv`
  - `tool_usage/tool_usage_task_interactions.csv`
  - `tool_usage/tool_usage_global_metrics.csv`
  - `tool_usage/tool_usage_nudge_counts.csv`
  - `tool_usage/tool_usage_nudge_comparison.csv`
- Main generation code:
  - `tool_usage/generate_tool_usage_summary.py`

## Source Tables and Inputs

- `Tool_CSV/tool_usage.csv`
  - Primary interaction source containing `participant_id`, `taskid`, `tool_used`, and `tool_decision_time`.
- `Tool_CSV/participants.csv`
  - Used to derive `nudge` group from `group_id`:
    - `group_id` 1-6 -> nudge `A`
    - `group_id` 7-12 -> nudge `B`
  - Also used to resolve `prolific_pid` -> integer `participant_id` for the inclusion list.
- `data_cleanup/filter_limesurvey_ids.csv`
  - Participant filter (the survey-confirmation list). The script resolves each prolific id to a participant id via `participants.csv`.

> **Inconsistency with the rest of the pipeline:** every other downstream script in this repository filters using `outputs/prolific_ids_with_counts.txt` (the telemetry-completeness list), while `generate_tool_usage_summary.py` filters using `data_cleanup/filter_limesurvey_ids.csv` (the survey-confirmation list). Participants who passed the survey but lack telemetry can therefore appear here while being excluded from other tables. The script's own top-of-file docstring still references `prolific_ids_with_counts.txt` and is stale.

## Important Derivation Rules

- For each `(participant_id, taskid)`, only the **latest** decision row by `tool_decision_time` is kept.
- Tool action mapping:
  - `tool_used=true` -> `Used`
  - `tool_used=false` -> `Skipped`
- Interaction ordering:
  - Latest-per-task rows are globally sorted by timestamp.
  - `Sequence_Order` is then assigned per participant as 1..N in that sorted order.
- Completion rate in participant summary:
  - `Total_Uses / (Total_Uses + Total_Skips) * 100`.

## Shared Keys Across Output Tables

- `Participant_ID` / `participant_id`: participant identifier.
- `nudge`: derived cohort label (`A` or `B`).
- `Task_ID` / `task_id`: task identifier.

## Table: `tool_usage_participant_summary.csv`

One row per participant in scope.

Columns:
- `Participant_ID`: participant id.
- `nudge`: participant cohort (`A`/`B`).
- `Total_Uses`: number of latest-per-task decisions marked used.
- `Total_Skips`: number of latest-per-task decisions marked skipped.
- `Completion_Rate`: percentage `Total_Uses / (Total_Uses + Total_Skips) * 100`, written as a string with a trailing `%` (e.g., `"83.33%"`, `"100.00%"`). Downstream consumers expecting a numeric column must strip the `%` suffix.

Primary use:
- Participant-level adherence to tool usage.

## Table: `tool_usage_task_interactions.csv`

Long-form interaction table (one row per participant-task latest decision).

Columns:
- `Interaction_ID`: sequential row id in export order.
- `Participant_ID`: participant id.
- `nudge`: participant cohort (`A`/`B`).
- `Task_ID`: task id.
- `Action`: `Used` or `Skipped`.
- `Sequence_Order`: participant-specific order index of decisions.

Primary use:
- Event-level analysis of use/skip behavior by task and sequence.

## Table: `tool_usage_global_metrics.csv`

Key-value metrics table with overall and task-specific counts.

Columns:
- `Metric`: metric name.
- `Value`: metric value.

Metric groups included:
- Overall:
  - `Total_Participants`
  - `Total_Tool_Uses`
  - `Total_Tool_Skips`
  - `Avg_Uses_Per_Participant`
  - `Avg_Skips_Per_Participant`
- Task-level:
  - `Task_<id>_Uses`
  - `Task_<id>_Skips`

Primary use:
- Quick dashboard-style summary for reporting.

## Table: `tool_usage_nudge_counts.csv`

Aggregated counts by `(nudge, task_id)`.

Columns:
- `nudge`: `A` or `B`.
- `task_id`: task id.
- `n`: total decisions in group (`used_count + skipped_count`).
- `used_count`: number of used decisions.
- `skipped_count`: number of skipped decisions.
- `avg_tool_uses`: `used_count / n` formatted to 4 decimal places (e.g., `"0.8125"`).

Primary use:
- Cohort/task-level comparison of tool uptake.

## Table: `tool_usage_nudge_comparison.csv`

One row per nudge cohort (`A`, `B`) summarizing tool-use rates averaged across tasks.

Columns:
- `nudge`: `A` or `B`.
- `n`: total latest-per-task decisions across all tasks for the cohort (`used + skipped`).
- `total_used_count`: total used decisions across all tasks.
- `avg_tool_uses`: mean of per-task `(used_count / n)` ratios across tasks present for that nudge, formatted to 4 decimal places. Note: this is an **unweighted average across tasks**, not `total_used_count / n`.

Primary use:
- Single-number tool-use rate per nudge cohort, comparable across tasks.

## Notes and Caveats

- Counts represent latest decision per participant-task, not raw event row totals.
- Column naming is mixed-case across files (for example `Participant_ID` vs `participant_id` style).

# Nudge To Completion Duration - Table Documentation

This section documents CSV outputs in `nudge_to_completion_duration/`, which capture elapsed time from nudge exposure to task completion.

## Scope

- Output tables documented here:
  - `nudge_to_completion_duration/nudge_to_completion_durations.csv`
  - `nudge_to_completion_duration/nudge_to_completion_avg_by_task_nudge.csv`
  - `nudge_to_completion_duration/nudge_to_completion_nudge_counts.csv`
- Main generation code:
  - `nudge_to_completion_duration/nudge_to_completion_durations.py`

## Source Tables and Inputs

- `Tool_CSV/code_snapshots.csv`
  - Event stream source with timestamps and `eventid`.
- `Tool_CSV/participants.csv`
  - Used to derive `nudge` cohort label (`A`/`B`) from `group_id`.
- `outputs/prolific_ids_with_counts.txt`
  - Participant filter; only listed participants are included.

## Important Derivation Rules

- Event mapping used:
  - Nudge event: `eventid=1`
  - Completion events: `eventid=3` or `eventid=4` (in practice we can't calculate duration to eventid=3 as no timestamps were collected for the event)
- Pairing logic per `(participant_id, taskid)`:
  - Select earliest nudge timestamp.
  - Select earliest completion timestamp that occurs at or after that nudge.
  - Duration = `completion_timestamp - nudge_timestamp`.
- Rows without valid nudge/completion pairing are excluded from duration CSV outputs.
- Duration formatting:
  - Numeric seconds with 2 decimals.
  - Human-readable `hh:mm:ss` rounded display.

## Shared Keys Across Output Tables

- `participant_id`: participant identifier.
- `nudge`: derived cohort label (`A` or `B`).
- `taskid` / `task_id`: task identifier (naming differs across files).

## Table: `nudge_to_completion_durations.csv`

Matched participant-task duration records.

Columns:
- `participant_id`: participant id.
- `nudge`: participant cohort (`A`/`B`).
- `taskid`: task id.
- `nudge_event`: fixed value `1`.
- `nudge_timestamp`: timestamp of selected earliest nudge event.
- `completion_event`: selected completion event id (`3` or `4`).
- `completion_timestamp`: selected completion timestamp.
- `duration_seconds`: elapsed seconds from nudge to completion.
- `duration_hh_mm_ss`: formatted duration string.

Primary use:
- Granular timing analysis at participant-task level.

## Table: `nudge_to_completion_avg_by_task_nudge.csv`

Average completion duration grouped by task and nudge cohort.

Columns:
- `taskid`: task id.
- `nudge`: `A` or `B`.
- `average_duration_seconds`: mean duration in seconds for the group.
- `average_duration_hh_mm_ss`: formatted mean duration.
- `sample_size`: number of matched participant-task records in the group.

Primary use:
- Compare timing differences by task and treatment cohort.

## Table: `nudge_to_completion_nudge_counts.csv`

Aggregated totals by `(nudge, task_id)` based on matched durations.

Columns:
- `nudge`: `A` or `B`.
- `task_id`: task id.
- `n`: number of matched participant-task records in the group.
- `total_duration_seconds`: sum of `duration_seconds` across the group.

Primary use:
- Cohort/task-level total time burden metric.

## Notes and Caveats

- Current script explicitly writes:
  - `nudge_to_completion_durations.csv` (via `outputs/nudge_to_completion_durations.txt` sibling CSV path)
  - `nudge_to_completion_avg_by_task_nudge.csv`
- `nudge_to_completion_nudge_counts.csv` exists in the folder but is not emitted by the current `nudge_to_completion_durations.py`; it appears to be generated by a separate/earlier step.

# Participant Profiles Schema - Table Documentation

This section documents `Aggregation/participant_profiles_schema.csv` using the transformation logic in `Aggregation/generate_participant_profiles_schema.py`.

## Scope

- Output table documented here:
  - `Aggregation/participant_profiles_schema.csv`
- Main generation code:
  - `Aggregation/generate_participant_profiles_schema.py`

## Source Tables and Inputs

- `data_cleanup/prolific_ids_with_counts.csv`
  - Driver list for included participants (`prolific_id`, `participant_id`).
- `tool_usage/tool_usage_participant_summary.csv`
  - Participant-level `nudge`, `Total_Uses`, `Total_Skips`.
- `tool_usage/tool_usage_task_interactions.csv`
  - Per-task used/skipped action source.
- `code_changes_with_tool/code_changes_after_tool_tasks.csv`
  - Task-level code-change and line metrics when tool was used.
- `code_changes_without_tool/code_changes_after_nudge_tasks.csv`
  - Task-level code-change and line metrics when tool was not used.
- `nudge_to_completion_duration/nudge_to_completion_durations.csv`
  - Duration source for completion time field.
- `bandit_comparison_with_tool/bandit_comparison_participant_submissions.csv`
  - Bandit counts/diffs when tool was used.
- `bandit_comparison_without_tool/bandit_comparison_nudge_participant_submissions.csv`
  - Bandit counts/diffs when tool was not used.
- `bandit_comparison_with_tool/bandit_comparison_type_changes.csv`
  - Bandit type changes when tool was used.
- `bandit_comparison_without_tool/bandit_comparison_nudge_type_changes.csv`
  - Bandit type changes when tool was not used.
- `Aggregation/results-survey641369.csv`
  - Full survey row appended to each participant profile (raw survey columns).

## Row-Level Construction Rules

- One output row per participant in `data_cleanup/prolific_ids_with_counts.csv` with both:
  - non-empty `participant_id`
  - non-empty `prolific_id`
- Task scope is fixed to tasks `1`, `2`, `3`.
- For each task, branch by `Task X tool use BOOL`:
  - `True` -> take task-level fields from *with-tool* sources.
  - `False` -> take task-level fields from *without-tool* sources.
- Completion time rule:
  - Populated from `nudge_to_completion_durations.csv` only when tool use is `True`.
  - Stored as `duration_hh_mm_ss` despite the column name using `DATE`.
- Type-change lists are sorted by numeric Bandit id (`B101`, `B311`, etc.) before joining.

## Base Columns

- `Prolific ID`: copied from `prolific_id`.
- `participant_id`: copied from input ids file.
- `Nudge`: from `tool_usage_participant_summary.csv` (`nudge`).
- `Number of tasks tool used`: from `Total_Uses` (integer-normalized).
- `Number of tasks tool not used`: from `Total_Skips` (integer-normalized).

## Repeated Task Block (for Task 1-3)

For each `X` in `{1,2,3}`, the same fields are generated:

- `Task X tool use BOOL`: derived from task interaction `Action == Used`.
- `Task X changed BOOL`: boolean from selected code-changes source.
- `Task X completion time DATE`: `duration_hh_mm_ss` from completion table (only when tool used).
- `Task X start_lines`: from selected code-changes source.
- `Task X End_lines`: from selected code-changes source.
- `Task X line_delta`: from selected code-changes source.
- `Task X issue count`: preferred from code-changes row if present; otherwise fallback to selected Bandit submission row.
- `Task X high severity count`: from selected Bandit submission.
- `Task X med severity count`: from selected Bandit submission (`medium_severity`).
- `Task X low severity count`: from selected Bandit submission.
- `Task X high severity diff`: from selected Bandit submission (`severity_diff_high`).
- `Task X med severity diff`: from selected Bandit submission (`severity_diff_medium`).
- `Task X low severity diff`: from selected Bandit submission (`severity_diff_low`).
- `Task X issue type ID`: comma-joined sorted `type_id` list.
- `Task X issue type name`: comma-joined sorted `type_name` list.
- `Task X issue change kind [fixed, common, new]`: comma-joined sorted `change_kind` list.

## Survey Column Appending

- All survey headers are appended after the modeled profile columns.
- Duplicate survey headers are made unique via suffixes like `__2`.
- Empty survey headers are renamed to `unnamed_<index>`.
- Survey join key:
  - Prolific ID taken from survey column index `7`.
  - When a Prolific ID has multiple matching survey rows, the row with the **most non-empty fields** is kept (not the first match). This favors fully-completed survey responses over abandoned ones.

## Notes and Caveats

- The script's top-of-file docstring claims output is `data_cleanup/participant_profiles_schema.csv`, but the active `OUTPUT_CSV` constant writes to `Aggregation/participant_profiles_schema.csv`. The on-disk artifact confirms `Aggregation/` is the canonical path.
- The field name `Task X completion time DATE` stores duration text (`hh:mm:ss`), not a date-time stamp.
- Bandit no-tool participant submissions are read directly from `bandit_comparison_without_tool/bandit_comparison_nudge_participant_submissions.csv`.
